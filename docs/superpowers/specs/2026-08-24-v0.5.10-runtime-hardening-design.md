# Company Intelligence Engine V0.5.10 — Runtime Hardening Design

**Date:** 2026-08-24  
**Status:** Proposed / approved direction, pending final human review of this written spec  
**Target branch:** `feat/v0.5.10-hardening`  
**Base:** `main` at v0.5.9

## 1. Purpose

V0.5.10 is a hardening release for Selykai Company Intelligence Engine. Its goal is to make the existing intelligence engine faster, cheaper, more predictable and easier to evolve before adding the V0.6 Decision Cockpit.

The release MUST preserve the current product philosophy and decision semantics:

- `FACT != INFERENCE` remains a hard architectural invariant.
- Official/commercial/web evidence keeps provenance, observation time and confidence.
- RNE commercial-reuse policy remains fail-closed: `blocked` and `unknown` MUST NOT trigger contact enrichment or commercial-action recommendations.
- The v0.5 scoring semantics remain unchanged. Refactors may move code but MUST preserve scoring outputs for identical inputs.
- Contact enrichment remains authenticated and on-demand only.
- Preview deployments remain read-only for production intelligence/workspace state.

V0.5.10 is deliberately NOT the Decision Cockpit release. It prepares the runtime and read-model foundations for V0.6 without mixing a new product surface with infrastructure changes.

## 2. Baseline findings

The review of v0.5.9 established the following production facts on 2026-08-24:

1. Vercel production functions currently execute in `iad1` while Neon is hosted in AWS `eu-central-1` (Frankfurt). A live `/api/health` request reported roughly 352 ms database latency, and the Vercel request identifier confirmed execution in `iad1`.
2. The persisted dataset is still small (5 companies at review time) but already contains 201 facts, 14 snapshots and 29 scores, with 214 recorded provider executions.
3. APILayer recorded 95 provider attempts, of which 74 were failures (77.9%). Serpstack succeeds using the `apikey` header, while the query-string auth fallback fails. Mediastack currently returns authentication errors with both attempted modes.
4. Search UX artificially holds successful results until at least 720 ms have elapsed.
5. The contacts endpoint calls the full company-analysis pipeline before resolving contact eligibility, causing unrelated provider work.
6. Adding a company to a watchlist also invokes a full analysis to ensure the company exists.
7. `persistCompanyAnalysis()` performs many sequential SQL round trips for establishments, facts, events and signals.
8. The company page starts some independent work sequentially, and the public company layout waits for optional authenticated watchlist context.
9. Monitoring intentionally analyzes companies sequentially. This protects providers today but will not scale by itself, and failed targets lack explicit retry/backoff state.
10. Scoring and provider implementation files have grown large enough that future feature work risks turning them into monoliths.
11. README/versioned CSS/test naming trails the actual release state and makes maintenance harder.

These findings define the hardening priorities. Micro-optimizations are secondary to network topology, unnecessary provider calls and database round trips.

## 3. Goals

### G1 — Co-locate compute and database

All normal Node.js Vercel Functions SHOULD execute in Frankfurt (`fra1`) so application compute is close to the Neon `eu-central-1` database.

Acceptance:

- project-level Vercel function region is configured to `fra1`;
- production deployment metadata shows `fra1` for Node.js functions after release;
- `/api/health` continues reporting database reachability and latency;
- no route is silently moved to Edge runtime as part of this release.

### G2 — Stop useless provider retries

Provider availability MUST be modeled at the operation/capability level rather than by the mere presence of a global API key.

For APILayer, at minimum the engine distinguishes:

- Serpstack / company SERP;
- Mediastack / company news;
- Positionstack / geocoding.

Authentication failures MUST open a shared circuit for the affected capability. During the circuit-open window the engine skips that capability instead of repeating known-failing HTTP requests for every company.

The circuit state SHOULD use existing shared persistence (provider cache/state) in v0.5.10 so a new database table is not required unless implementation evidence proves otherwise.

Acceptance:

- repeated analyses after an auth failure do not repeatedly perform both APILayer auth variants;
- a successful capability is not disabled because another APILayer product fails;
- provider health is observable in `/api/health` or an equivalent safe diagnostic without exposing secrets;
- the catalog differentiates configured, live, degraded/unavailable capabilities rather than reporting the entire APILayer family as healthy solely because a key exists.

### G3 — Remove artificial UX latency

Search results MUST display as soon as the actual API result is ready.

Acceptance:

- no fixed minimum 720 ms delay remains;
- loading animation remains available for genuinely slow requests;
- rapid successive searches cannot render stale earlier results over newer ones;
- abort/cancellation is used where appropriate to avoid useless in-flight searches.

### G4 — Introduce workload-specific intelligence execution

The engine MUST stop using a single exhaustive analysis pipeline for every user action.

The runtime will expose explicit execution intents/profiles:

- `interactive`: company page / API analysis where useful intelligence should load quickly;
- `monitoring`: exhaustive scheduled analysis with persistence and event detection;
- `contact`: minimum data needed to decide commercial reuse + verified domain + requested contacts;
- `bootstrap`: minimum canonical company persistence needed to attach a company to a watchlist;
- `refresh`: explicit exhaustive refresh initiated by a trusted/user action.

The exact TypeScript API may differ, but the intent MUST be explicit and testable rather than hidden behind ad-hoc booleans.

Provider work per intent:

- `contact` MUST NOT call BOAMP, BODACC, news or hiring when valid persisted eligibility/domain data already exists;
- `bootstrap` MUST NOT require full web/news/procurement/hiring enrichment just to create a canonical company row;
- `monitoring` remains allowed to run all configured intelligence sources because its purpose is change detection;
- `interactive` may use cached/persisted facts aggressively and refresh slow optional families without blocking all useful page content.

### G5 — Make persistence set-based

Company persistence MUST reduce sequential round trips to Neon.

The persistence layer should group writes by responsibility:

1. canonical company;
2. establishments/domains;
3. facts;
4. snapshot/events/signals;
5. score.

Where multiple rows of the same family are written, use a set-based write or bounded transaction rather than one awaited query per row.

Acceptance:

- no `for (...) await sql` pattern remains for normal multi-row persistence of facts/establishments/events/signals;
- atomicity is preserved for logically related state where partial writes would create invalid inference history;
- existing uniqueness/deduplication semantics remain intact;
- persistence regression tests prove repeated identical analysis is idempotent where it is expected to be idempotent.

### G6 — Keep optional UI data off the critical render path

Public company intelligence SHOULD begin rendering without waiting for optional authenticated watchlist state.

Acceptance:

- watch dock/authenticated context is placed behind an async/Suspense boundary or equivalent separation;
- the public page remains usable if Neon Auth is temporarily unavailable;
- independent timeline/history work is started as early as its dependencies allow;
- no client-side conversion is introduced merely to simulate streaming.

### G7 — Harden monitoring for controlled scale

Monitoring MUST remain provider-friendly while allowing controlled concurrency.

Design:

- group targets by SIREN as today so the same company is analyzed once per batch;
- process a small bounded number of companies concurrently (default implementation target: 2, configurable but hard-capped);
- add explicit retry/backoff semantics for transient failures;
- provider-wide auth/circuit failures should not hammer the provider for every target;
- successful targets keep normal daily/weekly scheduling;
- permanent company-not-found or invalid-data failures require a distinct state or long backoff rather than immediate repeated retries.

If persistent retry metadata requires a schema migration, that migration MUST be prepared and verified on a temporary Neon branch before production application. No production schema mutation is part of spec approval itself.

### G8 — Decouple observability from interactive latency

Provider telemetry MUST not add avoidable user-facing latency.

Design preference:

- provider calls produce lightweight telemetry records;
- interactive request paths flush telemetry using post-response/deferred work where Next.js/Vercel lifecycle guarantees execution;
- scheduled monitoring can keep stronger synchronous telemetry guarantees;
- failures to persist observability MUST NOT fail company intelligence.

Acceptance:

- provider success/failure remains measurable;
- interactive provider response time is not followed by a blocking database insert solely for telemetry when a supported deferred path is available;
- no unhandled promises are introduced.

## 4. Architecture

### 4.1 Runtime topology

Target production path:

```text
France / EU user
      |
      v
Vercel Node Functions — fra1
      |
      +---- Neon PostgreSQL — AWS eu-central-1
      |
      +---- French official providers
      +---- Commercial/web providers
```

Static assets remain globally delivered through Vercel's edge network. Only server compute locality is pinned for the database-heavy functions.

### 4.2 Intelligence orchestration

Separate orchestration from provider implementation.

Conceptual flow:

```text
Intent
  |
  v
Execution policy
  |- required evidence families
  |- optional evidence families
  |- freshness thresholds
  |- persistence policy
  |- event detection policy
  v
Provider/cache/persisted-data resolver
  v
Normalized facts
  v
Events/signals (when applicable)
  v
Existing scoring + commercial policy
  v
Result/read model
```

The engine should make freshness decisions centrally. Provider files should remain responsible for transport/normalization, not product-level decisions such as whether contact reveal needs BOAMP.

### 4.3 Persisted-first reads

A persisted fact may be reused when:

- it comes from the expected evidence family;
- its observation time is inside the freshness window for the current intent;
- commercial-policy-sensitive data is not stale beyond its stricter threshold;
- an explicit refresh was not requested.

Suggested initial freshness principles:

- official identity: long-lived, refresh on normal analysis/monitoring but reusable for bootstrap;
- commercial reuse policy: stricter freshness than generic identity;
- verified domain: reusable for contact flow when recently corroborated;
- BODACC/news/procurement/hiring: monitoring/refresh-oriented dynamic families;
- contacts: still fetched on demand and cached only under existing contact policy.

Exact TTL values belong in implementation constants and tests, not scattered magic numbers across routes.

### 4.4 Provider capability state

Provider state MUST be operation-scoped.

Conceptual state:

```ts
type ProviderCapabilityState = {
  providerId: string;
  capability: string;
  status: "unknown" | "healthy" | "degraded" | "auth_error" | "rate_limited";
  checkedAt: string;
  retryAfter?: string;
};
```

This state is diagnostic/runtime state, not company intelligence. It MUST NOT be mixed with company facts or signals.

Auth errors use a longer circuit than transient network failures. Rate limits respect provider retry metadata when available. A successful probe closes the capability circuit.

### 4.5 Read-model direction for V0.6

V0.5.10 SHOULD expose a clean latest-intelligence read path suitable for future watchlist prioritization, but MUST NOT add the Decision Cockpit UI yet.

The V0.6 cockpit will read already-computed intelligence and MUST NOT launch providers merely because the workspace dashboard opened.

This hardening release may add repository helpers that return the latest score/facts/triggers needed by a future read model if those helpers are also useful for current optimized flows.

## 5. Scoring refactor constraints

`lib/scoring/opportunity.ts` may be split into focused modules, for example:

```text
lib/scoring/
  fit.ts
  momentum.ts
  access.ts
  risk.ts
  confidence.ts
  opportunity-decision.ts
  opportunity.ts
```

However:

- `computeOpportunityScore()` remains the public compatibility entry point for v0.5.10;
- score version remains `intelligence-v0.5.0` unless scoring semantics actually change (they MUST NOT in this release);
- existing fixture inputs MUST return identical values, statuses, confidence and decision reasons unless a reason contains only corrected non-semantic wording explicitly covered by a test;
- policy post-processing remains separate from raw score computation.

The objective is maintainability, not tuning the business model.

## 6. UI/CSS consolidation

Version-number CSS files are technical debt, but a visual redesign is out of scope.

V0.5.10 SHOULD:

- consolidate active company intelligence styles into stable responsibility-based files/modules;
- consolidate workspace styles similarly;
- remove dead versioned styles only after verifying no active selector depends on them;
- keep current visual behavior and responsive layout unless a change directly fixes a performance/accessibility bug.

A large aesthetic redesign belongs to V0.6 or a separate UI project.

## 7. Error model

Expected user errors MUST stop surfacing as generic uncaught server-action exceptions.

Categories:

- validation error;
- authentication required;
- authorization denied;
- company not found;
- provider temporarily unavailable;
- provider capability misconfigured;
- persistence unavailable;
- commercial reuse blocked/unknown.

Server Actions should return/redirect with structured expected outcomes where practical. Unexpected faults remain exceptions and are observable.

The previous production error `SIREN invalide ou watchlist absente` should become a handled user-facing validation outcome rather than an error cluster.

## 8. Security and compliance

V0.5.10 MUST preserve or improve:

- server-side secrets only;
- no provider API keys in client bundles or responses;
- timing-safe cron secret comparison;
- authenticated workspace mutations;
- workspace membership checks on every mutation/query;
- `private, no-store` for contacts;
- commercial reuse fail-closed behavior;
- SSRF protections in first-party website verification;
- read-only preview behavior;
- current security headers.

Hardening SHOULD add a Content Security Policy only if it can be introduced without breaking Neon Auth/current assets and with testable deployment behavior. CSP is not allowed to become an unverified last-minute change in this release.

## 9. Documentation and versioning

After implementation:

- package/engine version becomes `0.5.10`;
- README reflects the actual V0.5.x feature set, including Momentum, policy-aware monitoring, actionable alert inbox, multiple watchlists and company watch dock;
- provider documentation explains capability-level health/circuit behavior;
- monitoring documentation explains concurrency/backoff;
- deployment documentation states the Vercel/Neon regional topology;
- no documentation should claim a provider product is healthy merely because a key is configured.

## 10. Test strategy

Implementation MUST follow TDD for changed behavior.

Required regression groups:

1. **Region/config validation** — repository config contains `fra1` and existing cron/git behavior remains present.
2. **Search latency/cancellation** — no artificial minimum delay; stale response cannot overwrite current query.
3. **Provider capability circuit** — auth error opens circuit; subsequent request skips; successful probe closes; one APILayer product failure does not disable another.
4. **Execution intents** — contact/bootstrap intents prove forbidden provider calls are not made.
5. **Commercial policy** — blocked/unknown still prevent contact enrichment and triggered prospecting decisions.
6. **Scoring parity** — existing v0.5 scoring fixtures remain byte/field equivalent where relevant.
7. **Persistence idempotency** — identical facts/snapshots/events keep dedupe semantics; batch persistence does not duplicate logical state.
8. **Monitoring** — same SIREN is analyzed once, concurrency cap is respected, failure backoff behaves correctly, successful schedule remains correct.
9. **Workspace actions** — expected validation failures are handled without becoming runtime crashes.
10. **Build verification** — full `npm run verify` succeeds before any completion claim.

## 11. Rollout

Changes should be delivered in small independently reviewable commits on `feat/v0.5.10-hardening`.

Recommended rollout order:

1. region + search latency quick wins;
2. provider capability health/circuit breaker;
3. execution intent layer + optimized contact/bootstrap paths;
4. UI async boundaries;
5. set-based persistence;
6. monitoring backoff/concurrency;
7. scoring/CSS structural refactors with parity tests;
8. docs/version cleanup;
9. full verification;
10. production deployment;
11. post-deploy health checks and provider-run comparison.

A production deployment MUST be followed by evidence checks:

- Vercel execution region is `fra1`;
- `/api/health` reports healthy DB/auth;
- database latency is materially lower than the reviewed `iad1` baseline;
- APILayer repeated auth-error attempts fall sharply;
- existing public search/company/workspace flows remain functional;
- no new runtime error cluster appears.

## 12. Non-goals

V0.5.10 MUST NOT:

- add a CRM pipeline;
- add autonomous outreach;
- add the Decision Cockpit UI;
- change prospect prioritization/scoring weights;
- bypass RNE reuse restrictions;
- enrich contacts in bulk;
- add speculative database indexes without `EXPLAIN` evidence;
- migrate frameworks/databases/auth providers;
- perform a visual redesign unrelated to hardening.

## 13. Definition of done

V0.5.10 is complete only when all of the following are true:

- runtime is region-aligned with Neon;
- search has no artificial delay;
- provider capabilities have shared failure suppression/circuit behavior;
- contact and watchlist bootstrap no longer require unnecessary exhaustive analysis;
- persistence avoids sequential row-by-row database loops for normal multi-row writes;
- optional authenticated watch context is not a blocker for public company rendering;
- monitoring has bounded concurrency and retry/backoff behavior;
- scoring policy/output parity is verified;
- documentation reflects the actual release;
- `npm run verify` is freshly green on the release head;
- production health checks confirm the intended runtime topology and no regression.

Only after this hardening release is stable should V0.6 implement the Decision Cockpit on top of the optimized persisted-intelligence read model.
