# Company Intelligence Engine V0.5.10 — Runtime Hardening

V0.5.10 is a performance, reliability and cost-control release. It deliberately does **not** change the scoring mathematics: the score model remains `intelligence-v0.5.0`.

## Main improvements

### Runtime locality

Vercel Node Functions are pinned to `fra1`, next to Neon PostgreSQL in AWS `eu-central-1`. Before this release production functions executed in `iad1`; the reviewed `/api/health` database check measured roughly 352 ms in that topology.

### Search responsiveness

The 720 ms artificial minimum loading delay was removed. Searches abort superseded requests and stale responses cannot overwrite newer results.

### Provider cost control

APILayer health is tracked independently for SERP, news and geocoding. Auth/rate-limit failures open shared capability circuits instead of being rediscovered for every company. Serpstack uses the authentication mode proven to work in the current environment.

INPI/RNE supplements are cached for one hour in shared Neon cache, reducing repeated serverless authentication and lookup work.

### Workload-specific execution

A simple watchlist add no longer launches the full intelligence pipeline. It persists the minimum official company identity required by the watchlist.

Contact reveal no longer runs BOAMP, BODACC, news and hiring. It reuses fresh persisted RNE commercial policy and verified domain first, then refreshes only required official/web evidence when necessary.

### Render path

The optional authenticated watch dock is isolated behind `Suspense`, so Neon Auth/workspace context no longer blocks the public company intelligence surface. Company analysis and timeline loading start concurrently.

### Neon persistence

Establishments, facts, events and signals are written set-wise with PostgreSQL `jsonb_to_recordset` instead of one awaited SQL statement per row. Fingerprints and existing deduplication rules are unchanged.

The recordset conversions were additionally validated against PostgreSQL 18 with read-only SQL because the Neon project had reached its branch-count limit during the verification session.

### Monitoring

Monitoring keeps one analysis per SIREN but processes a bounded number of distinct companies concurrently: 2 by default, hard cap 4.

Failures now update `next_check_at`:

- transient/unknown failure: +60 minutes ;
- company not found: +7 days.

No database migration was required.

### Observability

Interactive provider telemetry uses Next.js `after()` so persistence of `provider_runs` does not unnecessarily extend user-facing response latency. A safe synchronous fallback remains for contexts where deferred work is unavailable.

### Workspace feedback

Expected invalid-SIREN/company-not-found/watchlist-add failures are returned to the workspace as user-visible feedback rather than creating avoidable runtime exception clusters.

## Baseline used for post-deploy comparison

Review snapshot before V0.5.10:

- 5 persisted companies ;
- 201 facts ;
- 14 snapshots ;
- 29 scores ;
- 214 provider executions ;
- APILayer: 95 attempts, 74 failures (77.9%) ;
- INPI: 28 authentications for 32 company lookups ;
- Vercel functions: `iad1` ;
- Neon: `eu-central-1` ;
- `/api/health` database latency observed around 352 ms.

These are historical comparison values, not guaranteed production values after deployment.

## Post-deploy acceptance

After integration into `main`, verify:

1. production engine reports `0.5.10` ;
2. function execution is `fra1` ;
3. `/api/health` database latency is materially below the `iad1` baseline ;
4. repeated APILayer auth failures fall sharply ;
5. INPI authentication frequency falls due to shared cache reuse ;
6. search/company/workspace/contact flows remain functional ;
7. no new Vercel runtime error cluster appears ;
8. commercial-reuse guardrails remain fail-closed.

## Explicit non-changes

- no Decision Cockpit UI ;
- no CRM pipeline ;
- no autonomous outreach ;
- no scoring weight change ;
- no RNE policy bypass ;
- no bulk contact enrichment ;
- no speculative database indexes ;
- no aesthetic redesign.

The next product-level milestone can therefore build the V0.6 Decision Cockpit on a cleaner runtime foundation.
