# Monitoring and alerts

The monitoring layer turns the Company Intelligence Engine from an on-demand lookup tool into a change-detection product.

## Data model

Monitoring is scoped by workspace:

- a user belongs to one or more workspaces;
- a workspace owns watchlists;
- a watchlist contains companies already known by the intelligence database;
- each watched company has a daily, weekly or manual frequency;
- newly detected company events can generate deduplicated alerts for the workspace.

User identifiers are deliberately stored as opaque text values. This keeps the data model compatible with Managed Neon Auth or another authentication provider.

## Worker endpoint

Vercel Cron invokes the route with `GET`. Trusted infrastructure can also trigger it manually with `POST`.

```http
GET /api/internal/monitor
Authorization: Bearer <CRON_SECRET>
```

```http
POST /api/internal/monitor
Authorization: Bearer <CRON_SECRET>
```

The endpoint is server-only and must never be linked from the public UI.

Required production variable:

```text
CRON_SECRET=<long random secret>
```

When `CRON_SECRET` is configured in Vercel, Vercel Cron automatically sends the expected `Authorization: Bearer ...` header.

Optional tuning:

```text
MONITOR_BATCH_SIZE=20
```

The batch size is constrained to 1–100 by the application.

## Run strategy

For each batch the worker:

1. selects active watchlist entries whose next check is due;
2. groups entries by SIREN so one company is fetched only once even when multiple watchlists follow it;
3. analyzes companies sequentially to protect upstream public API rate limits;
4. persists new facts, snapshots, events, signals and scores;
5. creates workspace alerts only for newly detected events;
6. deduplicates alerts by workspace and event evidence;
7. schedules the next check according to the watch frequency.

A failed company analysis is not marked as checked. It remains due for a later retry. Before high-frequency production scheduling, a retry/backoff strategy should be added to avoid repeatedly hammering a failing upstream provider.

## Alert severity V0.3

- high: establishment growth, primary activity change;
- medium: head-office move, governance change, employer-status change;
- info: fallback for future event categories.

Severity is deterministic and explainable. It is not generated by an LLM.

## Vercel schedule

`vercel.json` configures one production cron:

```text
0 5 * * *
```

This triggers `/api/internal/monitor` every day at 05:00 UTC. The watchlist-level `next_check_at` field still decides whether each company is actually due, so weekly targets are not needlessly analyzed every day.

The application must be deployed and `DATABASE_URL` / `CRON_SECRET` configured before the scheduled route can succeed.
