# Monitoring and alerts

The monitoring layer turns the Company Intelligence Engine from an on-demand lookup tool into a change-detection product while keeping provider pressure bounded and explainable.

## Data model

Monitoring is scoped by workspace:

- a user belongs to one or more workspaces ;
- a workspace owns watchlists ;
- a watchlist contains companies already known by the intelligence database ;
- each watched company has a daily, weekly or manual frequency ;
- newly detected company events can generate deduplicated alerts for the workspace.

User identifiers are stored as opaque text values so the workspace model stays independent from a specific authentication schema.

## Worker endpoint

Vercel Cron invokes the route with `GET`. Trusted infrastructure can also trigger it manually with `POST`.

```http
GET /api/internal/monitor
Authorization: Bearer <CRON_SECRET>
```

```http
POST /api/internal/monitor
Authorization: Bearer <CRON_SECRET>
```

The endpoint is server-only. The Bearer secret is compared with `timingSafeEqual`.

Required production variable:

```text
CRON_SECRET=<long random secret>
```

Optional tuning:

```text
MONITOR_BATCH_SIZE=20
MONITOR_CONCURRENCY=2
```

- batch size: constrained to 1–100 ;
- concurrency: defaults to 2 and is hard-capped at 4.

## Run strategy V0.5.10

For each batch the worker:

1. selects active watchlist entries whose `next_check_at` is due ;
2. groups entries by SIREN so one company is analyzed only once even when several watchlists follow it ;
3. processes a small bounded number of distinct companies concurrently ;
4. invokes the explicit `monitoring` intelligence intent, which may run the exhaustive provider pipeline ;
5. persists facts, snapshots, events, signals and scores ;
6. creates workspace alerts only for newly detected events ;
7. deduplicates alerts by workspace and event evidence ;
8. schedules the next normal check after success ;
9. writes a future `next_check_at` after failure so the next cron does not immediately hammer the same target.

## Retry and backoff

V0.5.10 reuses the existing `watchlist_companies.next_check_at` field, so no database migration is required.

Current deterministic policy:

- successful daily target: next check +1 day ;
- successful weekly target: next check +7 days ;
- transient/unknown analysis failure: retry after 60 minutes ;
- company not found / permanent-looking identity failure: retry after 7 days.

Provider capability circuits add a second layer of protection: repeated auth/rate-limit failures can temporarily suppress only the failing provider capability without stopping official company intelligence.

## Alert severity

Severity stays deterministic and explainable. It is not generated by an LLM.

Examples:

- high: commercial-reuse change, establishment opening/growth, public-contract award, activity change ;
- medium: establishment closure, hiring change, financial change, head-office move, governance/employer change, BODACC activity ;
- info: fallback categories.

When commercial reuse is blocked or unknown, monitoring alerts remain usable for **veille uniquement** and include the action-policy guardrail.

## Vercel schedule

`vercel.json` configures:

```text
0 5 * * *
```

This triggers `/api/internal/monitor` every day at 05:00 UTC. Watchlist-level scheduling still decides which companies are actually due, so weekly companies are not analyzed daily.

## Operational checks

Monitor at least:

- number of targets / distinct companies per batch ;
- analyzed companies / failures ;
- alerts created ;
- actual concurrency ;
- provider auth/rate-limit errors ;
- targets repeatedly entering backoff.

The worker should remain conservative: raising concurrency above the application hard cap requires a deliberate code change and provider-capacity review.
